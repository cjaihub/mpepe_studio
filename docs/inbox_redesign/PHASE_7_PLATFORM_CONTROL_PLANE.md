# PHASE 7: PLATFORM CONTROL PLANE

## Objective
To decouple direct client-to-database writes from the mobile UI, moving the application to a true backend-managed messaging platform that supports multi-channel APIs, rate limits, and idempotency.

## The Send Path
The canonical send path is now structured as follows:

1. **Flutter UI:** User inputs text and hits send.
2. **MessageDraft:** A canonical `InboxMessage` object is constructed instantly, utilizing `uuid` to assign `clientCommandId` (guaranteeing one stable command identity for retries).
3. **Local Validation:** The Control Plane Service blocks empty messages natively.
4. **Backend Command:** Dispatched via `FirebaseFunctions.instance.httpsCallable('inboxSendMessage')`.
5. **Authorization / Connector Selection:** Handled backend side. The backend inspects `conversation.connectorId`, checks permissions, and selects the correct provider API module (e.g. Meta Graph API).
6. **Provider API & Response:** The backend waits for network response.
7. **Canonical Persistence:** Upon success (or error), backend writes to Firestore with the correct `deliveryState` (e.g., `sent`, `failed`).
8. **Realtime Event:** `ConversationStateProvider` implicitly picks up the `status` change via its `watchLatestMessages` Firestore listener.
9. **UI Update:** The UI updates its optimistic rendering smoothly.

## Command Identity
By stamping `clientCommandId` client-side, subsequent network retries generated by Flutter will not cause duplicate dispatches inside the backend, which ensures strict exactly-once idempotency logic across the distributed cluster.
